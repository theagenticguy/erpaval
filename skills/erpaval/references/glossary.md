# Glossary — ERPAVal vocabulary

Every other reference file links back here on first use of a coded identifier. If a term appears without a definition, it's defined here.

## Placeholder conventions

Worked examples throughout the skill use these tokens. Not literal strings — substitute real values per session.

| Token        | Meaning                                                                                   | Example values                                                          |
| ------------ | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `<hex>`      | Random lowercase hex suffix generated by `erpaval-new.py`. 6-8 chars.                     | `a1b2c3`, `9886af`                                                      |
| `<slug>`     | Kebab-case feature slug derived from the problem statement.                               | `oauth-pkce`, `retry-safety`                                            |
| `NNN`        | 3-digit zero-padded sequence number. Monotonic per project, assigned by `erpaval-new.py`. | `001`, `042`, `127`                                                     |
| `<domain>`   | Researcher-chosen topic slug for a Research YAML — one file per library or subsystem.     | `research-oauth`, `research-pydantic`, `research-sqlalchemy-async`      |
| `<category>` | One of the fixed category folders under `.erpaval/solutions/`.                            | `build-errors`, `api-patterns`, `conventions`, etc. (see `compound.md`) |
| `T-AC-X-Y`   | Task-packet filename mirroring the source EARS AC ID (`AC-X-Y`).                          | `T-AC-1-3.md`, `T-AC-2-1.md`                                            |

## Phases

ERPAVal has six phases. Each has a dedicated section in `SKILL.md`.

| Phase        | Role                                                                            |
| ------------ | ------------------------------------------------------------------------------- |
| **Explore**  | Understand the codebase. Skipped when `CL-DIR` returns `empty` (greenfield).    |
| **Research** | Fetch current API docs and version pins. Runs in parallel with Explore.         |
| **Plan**     | Derive the task graph from the EARS spec (or from findings if no EARS was run). |
| **Act**      | Implement via parallel subagents, one per leaf task.                            |
| **Validate** | Three layers: static, code quality, security.                                   |
| **Compound** | Extract lessons from the session and write to `.erpaval/solutions/`.            |

## Context packets (`CP-*`)

Files Claude writes per-session as hints informing Task-tool calls. Full index with schemas is in `context-packets.md`.

Mnemonic: `CP-INTAKE`, `CP-RECALL`, `CP-HMW`, `CP-EARS`, `CP-EXPLORE`, `CP-RESEARCH`, `CP-PLAN`, `CP-TASK-N`, `CP-VALIDATION`, `CP-LESSONS`, `CP-SESSION`.

## Classifiers (`CL-*`)

Runtime prompts the orchestrator runs to decide which phases to execute. Full prompt text is in `classifiers.md`.

| ID              | Decides                                          | Branches                           |
| --------------- | ------------------------------------------------ | ---------------------------------- |
| `CL-SCOPE`      | Coding vs non-coding task                        | Route to ERPAVal or upstream skill |
| `CL-REFINE`     | Did a non-coding user return with a build ask    | Re-enter `CL-SCOPE` or exit        |
| `CL-COMPLEXITY` | 1-file vs multi-module vs rebuild                | Skip ERPAVal for tiny fixes        |
| `CL-DIR`        | Empty vs existing vs rebuild-in-place directory  | Whether to run Explore             |
| `CL-RIGOR`      | Does the problem need HMW reframing or EARS spec | Run Framing substeps               |
| `CL-SPEC`       | Are PRD / stack / concept prerequisites ready    | Loop through upstream skills       |
| `CL-VALIDATE`   | All three validation layers green                | Pass or enter C4 fix cycle         |
| `CL-C2`         | Attempt-4 escalation disposition                 | fix-directly / respawn / C3        |
| `CL-DISP`       | Human disposition of Gate 2 findings             | Accept or enter C5 fix cycle       |
| `CL-LESSONS`    | Did this session produce novel reusable lessons  | Write to `solutions/` or skip      |

## Gates

| Gate       | Condition                                                    | Enforcement                  |
| ---------- | ------------------------------------------------------------ | ---------------------------- |
| **Gate 0** | Both Explore and Research tasks show `completed` in TaskList | Plan blocks until satisfied  |
| **Gate 1** | Plan reviewed and approved by the user                       | Act blocks until satisfied   |
| **Gate 2** | All three validation layers green or findings dispositioned  | Merge blocks until satisfied |

## Cycles (`C*`)

Named re-entry loops. Full triggers and protocols in `flow.md`.

| ID    | Name                      | Re-entry point  |
| ----- | ------------------------- | --------------- |
| `C1`  | Plan revision             | Plan            |
| `C1b` | Deeper context            | Explore         |
| `C1c` | Reframe problem           | Framing-HMW     |
| `C2`  | In-task fix (SendMessage) | Same subagent   |
| `C3`  | Missing prereq replan     | Plan            |
| `C4`  | Validation fail           | Act             |
| `C5`  | Human fix disposition     | Act             |
| `C6`  | Wave progression          | Act (next wave) |

## Wave

A set of Act-phase tasks with no dependencies between them — they run in parallel. Waves are not declared explicitly; they're derived from the task graph. A task joins wave N if every task it's `addBlockedBy` is in waves 1…N-1. Eager unblocking (C6) launches wave N+1 tasks as their individual blockers clear, without waiting for every wave N task to finish.

## EARS acceptance criterion (`AC-<story>-<n>`)

Numbered requirement inside an EARS spec. Each AC has a stable ID like `AC-1-3` (3rd AC of User Story 1) and carries `[P]` (parallel-safe) or `Dependencies: AC-X-Y`. The Plan phase derives `T-AC-X-Y` task packets directly. EARS methodology lives in `${CLAUDE_PLUGIN_ROOT}/skills/product-discovery/references/frameworks/ears.md`.

## Zones under `.erpaval/`

| Zone           | Gitignored? | Rationale                                              |
| -------------- | ----------- | ------------------------------------------------------ |
| `sessions/`    | yes         | Orchestrator-coupled, ephemeral, secrets surface       |
| `solutions/`   | no          | Durable compounding knowledge, benefits whole team     |
| `brainstorms/` | no          | HMW design intent, durable                             |
| `specs/`       | no          | EARS specs + derived tasks.md — traceable record       |
| `INDEX.md`     | no          | Discoverability pointer referenced from root CLAUDE.md |

Single `.gitignore` line: `.erpaval/sessions/`.
